# Lockstep

連線對戰的核心。程式在 [`src/net/LockstepSession.ts`](../../src/net/LockstepSession.ts)。

## 一句話

**只有按鍵狀態上線**，兩端各自跑同一份決定性模擬，對同一批輸入算出**位元完全相同**的世界。

每 tick 每人約 19 個位元組（含冗餘），伺服器對比賽內容一無所知。

## 為什麼是這個做法

替代方案是伺服器權威：客戶端送輸入、伺服器模擬、把狀態送回來。那需要伺服器有比賽的完整運算能力、在路徑上、而且離兩個玩家都不能太遠。

Lockstep 把伺服器從路徑上拿掉。代價寫在下面的「兩個代價」一節，而它們是被知情接受的取捨，不是疏漏。

## 輸入延遲

一個 tick 在雙方的輸入都到齊之前不能被模擬。所以本地輸入被排在 **`inputDelay` 個 tick 之後**才生效：

```
tick 100 按下的鍵  →  在 tick 103 生效（delay = 3）
                     這段時間剛好夠它飛到對面
```

延遲值**在大廳議定**，不是各機器自算。預設 3 tick（50 毫秒）。

**兩端必須用相同的值。** 值不同會讓雙方各自等待一格對方永遠不會送出的輸入 — 開打幾 tick 後永久卡住，症狀跟斷線一模一樣。

延遲越大越不容易卡頓，但操作越鈍。這是玩家實際會感覺到的那個取捨。

## 冗餘：一則訊息帶好幾格

輸入是**成批**送的，不是一格一則。所以一則訊息裡帶著最近幾 tick 的歷史。

在可靠的 WebSocket 上這只是便宜；在**不可靠的 WebRTC 資料通道**上，這是「一次丟包不會變成永久遺失」的唯一原因 — 下一則訊息會重複它帶過的那些格。

### 從固定寬度改成 ACK 驅動

窗口曾經是固定的 `max(12, inputDelay × 3)`，不管對方是不是早就收到了都照送。

現在每個封包都夾帶一個 `nextWanted` — **我方仍然需要對方補的最低 tick** — 而送方只送對方還沒確認的那些格，加上一個下限。

整個設計建立在一句不變式上：

> **一格輸入只有在對端於一個我方確實解析過的封包裡說「我已經有了」之後，才會離開送出緩衝區。**

這是它在結構上比固定窗口安全的原因，不只是比較省。固定窗口是依**時間**丟棄的，完全沒有收到的證據 — 上面那個陷阱的機制就在這裡。改成依證據保留之後，那個失效模式不可能發生。

**所以防止死鎖的不是下限，是保留規則。** 下限（`min(12, max(4, inputDelay + 1))`）的職責不同：它決定每一格在對方必須明確再要一次之前，會被重複送幾次。

三道防線：

1. **從沒收到過 ack 時，完全退回舊公式。** 這保證最壞情況不會比以前差。這個 sentinel 是承重的 — 少了它，一個永遠不 ack 的舊對端會讓窗口漲到 64 格上限，比以前**差四倍**。
2. **ack 單調前進。** 亂序抵達的舊 ack 是低估，只會多花流量；假裝它前進了才會丟掉還在路上的格。
3. **ack 上限鉗在我方實際送出過的最高 tick。** 超前的 ack 會縮小窗口，那是危險方向。灌水的對端是在餓死它自己 — 它動不了輸入格的值，也造不成 desync。

**自我修復**：封包丟了 → 對方的 ack 不前進 → 我方下一個封包的窗口自動長回去。

實測 payload（`lockstep.bandwidth.test.ts` 會把它釘住）：

| 情境 | 固定窗口 | ACK 窗口 |
|---|---|---|
| delay 3，乾淨 | 29.4 B/封包 | 18.8（−36%） |
| delay 8，20% 丟包 | 52.4 | 28.6（−45%） |
| delay 12，抖動（中繼） | 74.8 | 37.8（−50%） |

表頭砍不掉，所以總流量的降幅比這個小 — 直連約一成，中繼約三成。

## 校驗和與 desync 偵測

每 60 tick，兩端各自對自己的 `SimWorld` 取 FNV-1a 雜湊並交換。

雜湊必須對**每一個可能分歧的欄位**敏感 — 包括角色位置的低位元，那正是浮點誤差會現形的地方。

對不上時，session 進入 `desync` 狀態並**回報**。這是刻意的設計：**一個被回報的分歧，遠好過兩個畫面安靜地各說各話。**

## 卡頓，不是猜測

輸入沒到齊時，session **等**。它不猜。

猜測是 rollback 的工作，而這裡沒有 rollback。等待意味著跟不上的客戶端會拖住整場比賽。

**卡頓不是要補回來的債。** 兩端受同一批輸入閘住，所以誰都不會領先；把等待的時間累積下去只會讓比賽永久落後真實時間。

卡頓期間會重送，間隔是 **16, 16, 16, 32, 64 毫秒**然後維持在 64。節流永遠是依時間、不依呼叫次數 — 依次數會把速率綁在影格率上，而卡住的客戶端每個繪製影格只會被呼叫一次（17 fps 時就變成每秒兩次，一次丟包等於半秒呆滯）。

前幾次維持原本的 16 毫秒正是因為這個坑。之後退避是安全的，原因跟以前不同：以前的固定高頻是在替**盲目重送**買保險 — 不知道對方缺什麼，只能靠量。現在每次重送都帶著對方精確的 ack。

上限 64 毫秒（每秒 15 次）是必要的，因為重送同時也是我方 ack 的載具。

## 一格輸入一旦送出就是最終的

對手為某個 tick 保留它收到的**第一個**值。事後改變主意，代表兩邊用不同輸入模擬同一 tick。

**這在正常遊玩中就到得了**：一個卡住的客戶端會被持續詢問按鍵，而一個正在按鍵的玩家每次都給出不同答案。所以 session 對已經送出的 tick 拒絕重新取樣。

## 兩個代價

### 1. 沒有伺服器權威，改過的客戶端可以作弊

朋友之間用房號開的比賽，這是可接受的取捨。要堵住它得在伺服器上也跑模擬 — 無頭核心本來就允許。

### 2. 兩個玩家都等比較慢的那一個

沒有 rollback。跟不上的客戶端拖住比賽，而不是被預測著跳過去。

## 這一切怎麼保持不壞

**`Session` 介面把離線與連線壓成同一個問題**：這個 tick 可以跑了嗎？`LocalSession` 永遠回答可以。`BattleScene` 兩種模式走同一條路徑。

**測試在一條可控的爛連線上跑。** [`linkHarness.ts`](../../src/net/__tests__/linkHarness.ts) 提供一個帶虛擬時鐘的雙端連線，可以設定延遲、抖動、丟包與重排，全部由 seeded 產生器驅動 — 所以失敗是可重現的，而不是每週一次的謎團。

測到的包括：完美連線、100ms、200ms 加抖動、2% 丟包、20% 丟包，以及**四個變身大招在丟包連線下逐 tick 校驗和相同**（那是唯一伸進模擬的改動）。

**desync 的 bug 是最難手動重現的一類** — 需要兩台機器、一條爛網路和耐心。所以它們在這裡被抓。
