# 房間與狀態

狀態住在哪、怎麼被回收，以及**為什麼沒有資料庫**。程式在 [`server/rooms.ts`](../../server/rooms.ts)。

## 沒有資料庫

這不是還沒做，是**不需要**。

整個伺服器的相依只有兩個套件：`phaser`（客戶端用）與 `ws`。沒有 ORM、沒有資料庫驅動、沒有 Redis、沒有磁碟寫入、客戶端也沒有用 `localStorage`。

所有狀態就是一個行程內的 `Map`：

```ts
interface Registry {
  rooms: Map<string, Room>;   // 房號 -> 房間
  byConn: Map<string, string>; // 連線 id -> 房號
  rng: Rng;                    // 抽種子與場地
}
```

### 為什麼不需要

因為**沒有任何值得保存的東西**。

一個房間的存活期是「兩個人交換房號」到「比賽開始」之間的幾秒到幾分鐘。之後伺服器就退出路徑了 — 比賽在兩個客戶端之間直連進行，伺服器對比賽內容一無所知。

沒有帳號、沒有排行榜、沒有戰績、沒有存檔、沒有比賽紀錄。**沒有任何東西比行程本身活得更久。**

加一個資料庫會需要它自己的部署、備份、遷移與失敗模式，去保存一份幾分鐘後就無意義的資料。

### 這個決定的實際代價

**伺服器重啟會清掉所有等待中的房間。** 已經在打的比賽不受影響（它們是直連的），但正在大廳裡的人要重新開房。

**不能水平擴展。** 房間住在某一個行程的記憶體裡，所以自動擴展出來的第二台機器，會把同一個房間的兩個玩家放在不同的箱子上。這就是為什麼 [`fly.toml`](../../fly.toml) **釘死剛好一台常駐機器** — 那不是省錢，是正確性。

### 要加資料庫的話，動哪裡

`rooms.ts` 已經是對一個**顯式登錄表**操作的純函式集合 — 沒有 socket、沒有 `Date.now()`，時鐘當參數傳進來。要換成外部儲存，換掉 `Registry` 的實作並讓那些函式變成非同步，`index.ts` 幾乎不用動。

它會變成必要的時機是：想要跨行程共用房間（水平擴展）、想要在重啟後保留大廳、或者開始有帳號與戰績。**在那之前它只是一個可以壞掉的額外零件。**

## 房間生命週期

```
createRoom(connId, characterId)
 └─ 產生房號，建立者坐 0 號位
      joinRoom(connId, code)
       └─ 第二人坐 1 號位
            selectCharacter / setReady  （兩邊）
             └─ isReadyToStart → startMatch
                  └─ 抽 seed 與 stage，兩端收到相同的 matchStart
```

`leaveRoom` 在最後一人離開時刪掉房間。

**`reapExpired` 每 60 秒跑一次**，丟掉超過 30 分鐘的房間。被拋棄的房間否則是一個緩慢的洩漏 — 有人開了房念完房號然後關掉分頁，這種情形不會產生 close 事件的保證。

## 為什麼房間邏輯是純函式

`rooms.ts` **沒有 socket，也沒有 `Date.now()`**。時鐘當參數傳入。

這讓整個生命週期 — **包含那個半小時的過期** — 可以在毫秒之內測完，而且不用啟動任何伺服器。同時讓 `index.ts` 保持成一層薄薄的翻譯：socket 進來、翻成一次純函式呼叫、把結果翻回訊息送出去。

## 房號

字母表與驗證在 [`src/net/roomCode.ts`](../../src/net/roomCode.ts)，**客戶端與伺服器共用**。

放在共用處而不是伺服器上，是因為大廳也需要它：它過濾玩家能打什麼字，所以打錯在按鍵當下就被拒絕，而不是等一下變成一次失敗的加入。

**`0`/`O` 與 `1`/`I`/`L` 被排除**，因為房號是**用唸的** — 兩個人在講電話或坐在旁邊。

> 房號輸入曾經有一個 bug：`F` 在其他每個畫面都是確認鍵，而輸入框沿用了那個習慣 — 所以打 `2F7KHN` 的 `F` 會直接送出已輸入的兩個字，玩家對著一個念得完全正確的房號收到「查無此房」。修正記在 FIX_NOTES v1.4.1；現在 e2e 會把整個 31 字的字母表都打一遍。
