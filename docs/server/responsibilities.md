# 伺服器職責

它做什麼，以及**更重要的：它不做什麼**。程式在 [`server/`](../../server/)，三個原始檔。

## 它不模擬

Lockstep 需要的是「兩端對輸入有共識」，不是「兩端服從一個權威」。所以這個行程唯一決定的，是**兩個客戶端沒辦法各自決定**的那些事：

- 誰在哪個房間
- 他們必須共用的**種子**與**場地**
- 他們必須共用的**輸入延遲**

其餘一切都在客戶端算。伺服器對誰打中誰、誰血多、誰贏了**完全沒有意見**。

## 它做的三件事

**1. 房號登錄。** 建房、加入、離開、選角、準備、開賽。

**2. 信令中轉。** 兩端要建立 WebRTC 直連時，透過它交換少量協商訊息。

**3. 中繼後備。** 直連失敗時，遊戲流量改走它轉發。

第三點是它唯一會碰到遊戲流量的情況，而且是**不得已才走的路**。詳見 [傳輸與協定](../networking/transport-and-protocol.md)。

## 它幾乎與手感無關

因為比賽是直連的，**伺服器只在交換房號的那幾秒被需要**。

這帶出兩個結論：

- 一個閒置就睡眠的免費方案在這裡是合理的取捨
- 它的地區幾乎不影響遊戲手感

（走中繼後備時就不是這樣了 — 那時它在路徑上，地區就很重要。）

## 兩個誠實的限制

### 1. 改過的客戶端可以作弊

沒有伺服器權威，就沒有東西能反駁一個宣稱自己沒被打中的客戶端。

**對朋友之間用房號開的比賽，這是可以接受的取捨。** 要堵住它，得在伺服器上也跑模擬 — 無頭核心本來就允許這件事（`tsconfig.server.json` 已經把 `src/sim`、`src/fighters`、`src/combat` 全部含進來，即使今天的伺服器只用到其中幾個角落），但目前的範圍沒有這個需求。

### 2. 兩個玩家都等比較慢的那一個

沒有 rollback，所以跟不上的客戶端會拖住整場比賽，而不是被預測著跳過去。

## 端點與限制

| | |
|---|---|
| `GET /healthz` | 回 `ok`。部署平台的健康檢查用 |
| `WS /ws` | 大廳與遊戲流量，同一個 socket |
| 訊息速率上限 | 每連線每秒 **300** 則 |
| 大廳訊息大小上限 | 16 KB（信令 12 KB） |
| 閒置連線逾時 | 5 分鐘（從未加入房間者） |
| 房間 TTL | 30 分鐘 |

**300 則/秒約是遊玩需求的五倍。** 一場比賽每秒約 60 則輸入訊息加上偶爾的校驗和；留這麼多餘裕是為了讓從背景分頁切回來、正在追趕的客戶端可以在一影格內爆送十幾個 tick。

## 靜態檔案

`server/main.ts` 用同一個行程同時服務**打包好的客戶端**與 **WebSocket**，所以頁面連 `/ws` 不需要知道主機名稱，也就沒有 CORS 或憑證問題（平台終結 TLS 之外）。

`startServer` 接受 `staticDir: null` 以提供純 API 伺服器，搭配 `VITE_WS_URL` 讓另外託管的客戶端指過來。**同源只是預設值，因為它不需要設定，不是因為兩半綁在一起。**
